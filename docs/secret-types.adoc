= Secret Types: a scoped information-flow specification proposal
:toc: macro
:toclevels: 3
:icons: font
:revdate: 2026-09-27

[abstract]
This note records a concrete first model for issue #32: a two-level,
confidentiality-oriented information-flow discipline for pure, deterministic,
total programs. It separates that model from the existing epistemic interfaces
and from neighbouring type projects. This is a specification proposal, not an
implemented API or security guarantee: there is no `Secret` type, IFC calculus,
declassification rule, or noninterference theorem in this repository today.

== Boundary and history — 2026-10-04

**Owner decision (2026-10-04): `hyperpolymath/secret-types` is the standalone
home for secret types.** This note is retained in `epistemic-types` as the
boundary/history record: it explains why this repository does not host a
`Secret` API or an information-flow implementation, and it points to the
standalone work. No `Secret` type, IFC calculus, declassification rule, or
noninterference theorem is added here.

Two rulings govern the standalone specification:

* **D153** — A secret type is a value whose flow is constrained by a
  confidentiality label with explicit declassification, registered in the
  type-family map on that boundary.
* **D154** — Reuse an existing lattice (two-point first, then general), prove
  noninterference, and allow declassification only at explicit audited points.

The proposal below (two labels `Public ⊑ Secret`, dependency join, low-observer
attacker, termination-insensitive noninterference target) remains the starting
point for the standalone specification, read in the light of D154: the two-point
lattice comes first and generalises only if the typing rules require it, and
declassification is admitted **only at explicit audited points** with a stated
authority and policy. The baseline's blanket "no declassification" is the safe
default for this note, not the final policy for the standalone design.

Status of the related issues:

* `epistemic-types#29` (preservation of the original note) is resolved and
  stays closed.
* `epistemic-types#32` ("Specify an in-repository security model for secret
  types") is obsolete as titled: the work moves to `hyperpolymath/secret-types`
  (D153/D154). Until that transfer lands, this note and issue #32 remain the
  record; the replacement issue is the transferred #32 itself, not a duplicate.

== Decision offered for issue #32

Issue #31 landed this research direction here as documentation. Issue #32 asks
for the first semantic boundary, not for an Agda module. This pass proposes the
following decisions for review:

* **Accept as a distinct research target:** static confidentiality / information
  flow, with the minimal baseline specified below.
* **Reject as an extension of the epistemic core:** do not identify a security
  label with an epistemic standpoint `κ`, and do not add an
  `EpistemicTypes.Secret` API on the strength of the current interfaces.
* **Conditionally accept `Secret ℓ A` as a candidate value type:** it can
  represent a value classified at security label `ℓ` inside a separately
  specified IFC calculus; this does not accept it as a public API today.
* **Reject a wrapper-only security claim:** `Secret ℓ A` alone does not define
  program flows or prove noninterference. The calculus must include the rules
  for dependencies and observations.
* **No Agda API or new repository yet:** use this note as the decision record
  while the exact calculus and the correct home for it are reviewed. Section
  <<repository_boundary_and_exit_criteria>> sets the early repository gate.

These are proposed model decisions, not a claim that the project has accepted an
implementation. Keep issue #32 open until the owner accepts or revises the
baseline and placement decision.

== What this repository currently provides

The current code offers concepts that may be useful when designing a security
model, but their present meanings are narrower:

* `Modality` in `src/EpistemicTypes/Base.agda` is an indexed family `E κ A`
  with a mapping operation. It does not assign confidentiality labels or
  restrict who can observe a value.
* `Access.Preorder` and `AccessibleModality.increase` in
  `src/EpistemicTypes/Access.agda` let an instance interpret an order and
  transport `E κ A` along it. The example reading is epistemic access from a
  less-informed to a more-informed standpoint. The generic preorder does not
  specify a security policy, a least element, joins, clearances, or program
  flow rules.
* `BeliefModality` omits a `reflect` field. This says that the generic record
  interface does not provide a factivity operation. It does **not** hide a
  concrete representation, prevent pattern matching, stop a client from
  exposing data through another operation, or establish confidentiality.
* `FactiveModality.reflect : E κ A -> A` is an epistemic factivity interface.
  It is not a declassification policy. Conversely, omitting `reflect` is not,
  by itself, an information-flow proof.
* `Warrant` separates evidence tokens from an explicit soundness map, and
  `ProofTransport` proves claims relative to a caller-supplied meaning and
  checker. Neither module models secrecy, identity, cryptography, or a physical
  access-control system.
* `Echo` certificates relate a residue to an observation under a supplied
  contract. `BoundedEcho` bounds a supplied residue measure. Its grade is not
  inherently a number of leaked bits, entropy, or a declassification budget;
  such a meaning would need its own measure and theorem. See
  link:continuity-foundations.adoc[continuity foundations].

At this revision, the proof gate recursively checks the Agda modules under
`src/EpistemicTypes/` (17 source modules) using `--safe --without-K`, with no
standard-library dependency. These proofs establish only the propositions
encoded in those modules. Safe type-checking is not a general security
certification, and it does not supply missing security semantics. The root
`SECURITY.adoc` is the repository's vulnerability-reporting policy; it is not a
program information-flow model.

== Proposed baseline model

=== Use case and trust boundary

The first example domain is a pure, total policy/configuration function that
receives a public request and a trusted private setting and returns an explicitly
classified result. A public observer may choose and know the request, but must
not learn anything about the private setting from public outputs. This is a
small, concrete information-flow problem; it does not claim to model a deployed
service.

Source labels are trusted inputs to the model. The checker cannot infer from an
arbitrary value whether it is genuinely public or private. In particular, any
real application must justify the initial classification at its input boundary;
a type annotation alone cannot authenticate that boundary.

=== Labels, order, flows, and clearances

For the first model, use exactly two labels:

[source,text]
----
Label = { Public, Secret }
Public ⊑ Public       Public ⊑ Secret       Secret ⊑ Secret
                       (no proof of Secret ⊑ Public)
⊥ = Public            ⊤ = Secret
----

Read `ℓ ⊑ ℓ'` as: data classified at source label `ℓ` may flow to a destination
classified at `ℓ'` without becoming less protected. Thus `Public` is the bottom,
`Secret` is more restrictive, and an ordinary flow may raise sensitivity but may
not lower it. Combining dependencies uses the least upper bound:

[cols="1,2",options="header"]
|===
| Inputs | Resulting label
| `Public ⊔ Public` | `Public`
| `Public ⊔ Secret` | `Secret`
| `Secret ⊔ Public` | `Secret`
| `Secret ⊔ Secret` | `Secret`
|===

A clearance is also a label. A value at `ℓ` is within clearance `c` exactly when
there is a witness of `ℓ ⊑ c`. A `Public` observer can therefore observe public
values only; a `Secret` clearance is permitted to observe either label *inside
the model*. Such a witness states a policy relation. It does not prove a person's
identity, authenticate a credential, or enforce access control at runtime.

The two-point lattice is the specification baseline, not a claim that a general
`SecurityLattice` interface is already justified. General labels should be added
only after the two-point model establishes which operations and laws the typing
rules actually require. A bounded join-semilattice may suffice for upward
combination; requiring meets or a richer lattice without a theorem would be
premature.

=== Attacker and observations

The baseline attacker is a low-clearance observer who:

* may choose and know all public inputs;
* may observe the explicitly public projection of a program's result; and
* may compare results from executions with the same public inputs and different
  secret inputs.

The model assumes that the attacker cannot inspect secret values directly,
forge trusted source classifications, or obtain a privileged clearance witness.
Those are assumptions of the model, not properties established by Agda. Since
the initial language is pure, deterministic, and total, it has no I/O, mutable
state, concurrency, exceptions, divergence, or observable termination. Timing,
space, cache, storage, network, speculative-execution, and other side channels
are outside the observation model. Adding any of these later requires a new
semantics and threat analysis.

=== Permitted and forbidden flows

The baseline permits:

* explicitly trusted public inputs to remain public or be raised to `Secret`;
* secret inputs to remain secret; and
* values with multiple dependencies to receive their join label.

It forbids an ordinary `Secret`-to-`Public` flow. This includes implicit flow:
if a secret condition selects between two different public results, that result
must not be accepted as public merely because neither branch directly returns a
secret value. The core expression rules must account for the condition as a
dependency. If the language later adds commands or effects, its program-counter
or equivalent control-dependence discipline must be specified as well.

There is **no declassification** in this baseline: no downgrade operation,
release budget, trusted declassifier, or authorization policy. A deliberate
release is still a forbidden flow until a separate policy states who may release
which information, under what evidence or capability, and which security theorem
is preserved. An authorized-read judgement is not itself declassification, but
an accessor exposed to untrusted program code could still create an output leak;
its use must be included in the language semantics and proof.

=== Target semantic property

Let a machine state be a pair of public and secret inputs. Define two states to
be low-equivalent when their public components are equal, with no constraint on
their secret components. Let `run c s` be the result of evaluating program `c`
in state `s`, and let `observePublic` select exactly the output visible to a
`Public` observer.

Because the model admits only total programs, there is no separate termination
observation. The noninterference target is:

[source,text]
----
For every program c well-typed to produce a Public output,
for all public inputs p and secret inputs h₁, h₂:
  observePublic (run c (p, h₁)) = observePublic (run c (p, h₂))
----

This is a two-level, termination-insensitive noninterference property for the
specified pure language: changing only secret input cannot change a public
observation. It is a theorem the future typing rules must prove, not an axiom,
field, or consequence of having a `Secret ℓ A` wrapper. If partiality or
observable termination is introduced, the observation relation must be revised
and the corresponding termination-sensitive or termination-insensitive claim
stated explicitly.

The required future positive/negative examples are consequently clear:
well-typed public results whose value does not depend on the secret must be
accepted; a direct secret return and a public result selected by a secret branch
must be rejected. These controls test the intended flow rules, but do not replace
the semantic theorem.

=== Candidate type shape, and its limit

A future value-level surface could include signatures resembling the following;
these are schematic, not Agda declarations or an accepted API:

[source,text]
----
Secret   : Label -> Set -> Set
raise    : ℓ ⊑ ℓ' -> Secret ℓ A -> Secret ℓ' A
combine  : Secret ℓ A -> Secret m B -> Secret (ℓ ⊔ m) (A × B)
----

These operations express classification, safe upward propagation, and joining
dependencies. They do not define the expression language, its control-flow
rules, or the public observation function. An unrestricted
`Secret ℓ A -> A`, whether called `reflect`, `reveal`, or `readAt`, is not part
of the program interface. A future observer API would need a precise clearance
semantics and a trusted boundary; it still would not authenticate an actual
principal or prove noninterference on its own.

== `Access.Preorder` is not the security interface

The two domains share the *shape* of an order, but not its interpretation or
required operations:

[cols="1,2,2",options="header"]
|===
| | Epistemic access in this repository | Security flow in the proposed model
| Index | Standpoint `κ` | Confidentiality label `ℓ`
| Order reading | `κ ≤κ κ'`: `κ'` is at least as informed as `κ` | `ℓ ⊑ ℓ'`: information may flow from `ℓ` to no-less-restrictive `ℓ'`
| Transport / use | `E κ A` transports to `E κ' A` | Data dependencies join; reading requires `ℓ ⊑ clearance`
| Extra structure needed | Reflexivity and transitivity | The chosen label order, public bottom, join, clearance interpretation, source/flow typing, and low-equivalence semantics
|===

`Access.Preorder` supplies only reflexivity and transitivity. It has no label
bottom, join, classification policy, low-equivalence relation, or noninterference
semantics. Reusing it as the public security API would make the indices look
interchangeable when they are not. The baseline therefore calls for a distinct
security-label definition and relation. Shared proof lemmas for preorders could
be considered later, but that would be code reuse only, not a semantic
identification.

[[repository_boundary_and_exit_criteria]]
== Repository boundary and exit criteria

There is a real **semantic** boundary: epistemic availability asks what is
available at a standpoint; information-flow security asks whether changes in
highly classified inputs can affect a lower observer. The common fact that both
may be indexed by an order does not make one an extension of the other.

The neighbouring projects narrow the repository decision:

[cols="1,2,2",options="header"]
|===
| Project | Existing responsibility | Relevance and limit for this proposal
| `epistemic-types`
| Standpoint-indexed modalities, warrants, and proof transport
| Correct home for this decision note because the research began here; not the home of an `E κ A`-based confidentiality API.
| `systemet` / `anytype`
| SystemET specifies an L2 ordered-semiring grade algebra; Anytype is its checker kernel.
| SystemET's merged MECH-2 work proves a bounded-distributive-lattice grade instance, including the two-point `Low ≤ High` lattice. Anytype issue #15 remains open for porting the lattice/cost/product instances to the kernel. This is a promising home for the *grade algebra* part, not evidence of a program-level IFC or noninterference theorem. The grade operations' usage meaning must not be silently equated with confidentiality propagation.
| `echo-types`
| Proof-relevant fibers / residues and structured information loss
| `EchoSecurity` proves a no-section / no-recovery property for a collapsing exit map; that is not low-observer noninterference. Its adjacency note records a formalized relational-IFC comparison and leaves comparison with type-theoretic IFC open, so novelty claims for a new calculus need that comparison.
| `tropical-types`
| Resource-grade algebras and worst-case bounds
| Resource grades are not confidentiality labels; a resource bound is not a leakage bound without a separate measure and theorem.
|===

=== Placement decision for the next step

**Do not create a new repository from issue #32 alone, and do not add a
`Secret` module under `EpistemicTypes`.** Keep this specification here as the
record of why the question arose. Before writing proof code, make one explicit
cross-repository choice:

. If the desired contribution is the lattice/grade instance within a graded
  language, coordinate with SystemET/Anytype and prove the mapping from its L2
  grade operations to this confidentiality interpretation.
. If the desired contribution is a standalone IFC calculus—with its own
  expression and control-flow rules, low-equivalence semantics, and
  noninterference theorem—that cannot be hosted in SystemET without conflating
  resource use with confidentiality or changing its theory, then a separate
  repository is justified. Make that split **before** growing an API or runtime
  prototype, and compare the calculus against the type-theoretic IFC literature
  and Echo Types' open adjacency question.

On the evidence checked for this note, the answer is: **separate from
`epistemic-types` as a type/API; no new repository yet.** A candidate host for a
grade-only realization already exists, while the independent-calculus case
needs the owner to choose that larger deliverable and resolve the neighbor
comparison. This is an early gate, not a commitment to keep security work in
this repository indefinitely.

== Explicit non-claims

This proposal does not claim that the following exist or have been proved here:

* a `SecurityLattice`, `Secret`, `classify`, `declassify`, or clearance API;
* an implemented information-flow type system or a proof that forbidden flows
  cannot occur;
* the noninterference theorem above;
* authenticated principals, runtime access control, cryptographic secrecy,
  secure erasure, zeroization, or protection from timing, cache, storage,
  network, or other side channels;
* linear or single-use handling of secret values;
* a connection from `EchoBridge.Grade` to bits, entropy, or a security budget;
* a transfer of proof from another repository's algebra, type checker, or
  runtime into this Agda development.

`--safe --without-K` establishes only the propositions actually encoded and
checked by Agda. It does not validate the adequacy of this proposed attacker
model or any external implementation. Any future integration must name exact
source revisions, state the compatibility claim, and add a reproducible check
before this project relies on it.

== Review checklist before implementation

Issue #32's first-stage acceptance should require agreement on all of the
following, not just agreement on the name `Secret`:

. Accept or revise the two-level public/secret labels and their order direction.
. Confirm the pure, total policy/configuration use case and the low-observer
  capability boundary.
. Confirm that declassification and runtime/side-channel claims are out of
  scope.
. Accept the exact low-equivalence/noninterference statement and require a
  future type-soundness proof for the chosen calculus.
. Decide whether to target SystemET/Anytype as a grade instance or open a
  standalone calculus repository before API work.
. Only then specify syntax, typing rules, and positive/negative proof controls.

The follow-on implementation stages remain separate: a focused formal module
and expected-rejection fixtures; the semantic noninterference proof; and, only
if required, a runtime correspondence argument. None is part of this issue's
prose-specification step.
